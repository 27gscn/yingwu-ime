# 应物输入法

> **《应物汉字音形衡码输入方案》**
> 版本 0.57-heng　｜　Windows TSF 原生输入法　｜　独立安装，无需任何第三方输入法框架

**应物输入法**是软件，**《应物汉字音形衡码输入方案》**是它实现的编码方案。仓库里以 `hengma` 开头的方案与词典文件名指的是后者，为保持历史编码有效而未改名。

本方案以**完整拼音**为骨（音），以**字形结构与部首**为翼（形），做确定性消歧：

```text
单字：  全拼  →  结构码  →  部首码
词组：  连续全拼  →  第一组结构＋部首  →  可选第二组结构＋部首
```

- 全程离线；不使用语言模型、小模型、云端预测或用户词频学习
- 候选顺序只由静态词典的固定权重决定，同样的输入永远得到同样的结果
- 结构码与部首码都是**可选校验**，不要求每次输入都打满

# 一、编码规则

## 1.1 总览

一个字的编码最多三段，逐段收窄候选范围：

| 段 | 键数 | 内容 | 是否必需 |
|---|---:|---|---|
| 音 | 1—6 | 该字的**全拼**（不带声调） | 必需 |
| 形·结构 | 1 | 该字的**整体结构**，取自 `z s b d p` | 可选 |
| 形·部首 | 1 | 该字**首部件／部首名称的拼音首字母** | 可选，且须在结构码之后 |

以「清」为例：

```text
qing        →  请 轻 清 青 情 晴 …    全部 qing 音的字
qing z      →  请 轻 清 情 晴 …       只剩左右结构的
qing z s    →  清 碃                  左右结构、部首为「水」的
```

三段合起来 `qingzs` 即「清」的完整编码。

## 1.2 音：全拼

使用不带声调的标准汉语拼音，`ü` 写作 `v`。

多音字按读音分别成码：「行」有 `hang`、`heng`、`xing` 三个读音，因而有三条独立的编码链。

按字频加权的全拼长度分布：

| 全拼键数 | 占比 |
|---:|---:|
| 1 | 0.84% |
| 2 | 35.63% |
| 3 | 36.77% |
| 4 | 20.86% |
| 5 | 5.72% |
| 6 | 0.20% |

平均 2.96 键。这是编码成本的主体，占总击键数的 81%。

## 1.3 形·结构码（5 键）

| 键 | 结构 | 判定依据 | 字数 | 占比 |
|:--:|---|---|---:|---:|
| `z` | 左右、左中右 | IDS 为 `⿰` `⿲` | 5,815 | 66.4% |
| `s` | 上下、上中下 | IDS 为 `⿱` `⿳` | 1,985 | 22.7% |
| `b` | 包围、半包围 | IDS 为 `⿴⿵⿶⿷⿸⿹⿺` | 731 | 8.3% |
| `p` | 品字形、交叠、其他特殊 | 三叠式、`⿻`，以及无法归类者 | 154 | 1.8% |
| `d` | 独体 | 单部件，或约定为整体的常用字 | 72 | 0.8% |

判定由 `data-tools/generate_hengma.py` 依汉字的 IDS（表意文字描述序列）机械推导，规则依次为：

1. 若该字在 `SINGLE_STRUCTURE_OVERRIDES` 名单内 → `d`。这份名单收录「中木本末未米术朱束东车申甲由田王玉井开丰手牛羊生年午果来夫天大太犬丈支十干于土士工〇」等按习惯视为整体的常用字，避免机械拆分把「木」判成交叠结构。名单刻意保守，拿不准的字一律留在 `p`。
2. 若 IDS 数据缺失 → `p`。「结构未知」与「独体」是两回事：`d` 是一个肯定判断，而 `p` 本就是兜底类。（`𰻝` 有五十余画却无 IDS 数据，正属此类。）
3. 若 IDS 说它是单个部件 → `d`。
4. 若构成三叠式（品、森、晶、众）→ `p`。
5. 其余按顶层 IDS 运算符归入 `z` / `s` / `b`；`⿻`（交叠）及任何其他运算符 → `p`。

> **这个键很弱，这是设计取舍而非疏忽。** 三分之二的汉字是左右结构，`z` 一个键就覆盖 66.4%，信息熵只有 1.339 bit，而 5 键字母表的理论上限是 2.322 bit（效率 57.7%）。它的价值不在区分力，而在**几乎不需要知识**——看一眼就知道是左右还是上下。真正的区分力来自下一段。

## 1.4 形·部首码（22 键）

### 取码原则

**取该字首部件（通常即部首）的常用名称的拼音首字母。**

关键在于取的是**名称**而非字形本身的读音：

```text
清 → 部首 氵 → 名称「水」 → shuǐ → s
请 → 部首 讠 → 名称「言」 → yán  → y
轻 → 部首 车 → 名称「车」 → chē  → c
情 → 部首 忄 → 名称「心」 → xīn  → x
晴 → 部首 日 → 名称「日」 → rì   → r
```

因此**偏旁与其本字取同一个码**：`氵` 和 `水` 都是 `s`，`讠` 和 `言` 都是 `y`，`亻` 和 `人` 都是 `r`。写法变了，名字没变，码就没变。

### 不在表中的部件

回退到**该部件自身读音的首字母**。例如「歹」→ `dǎi` → `d`，「隹」→ `zhuī` → `z`，「耒」→ `lěi` → `l`。

若该部件连读音数据也没有，则该字**没有部首码**，编码止于两段。8,757 个字中有 8,584 个带部首码（98.0%），其余 173 个只有全拼和结构码。

## 1.5 单字完整示例

同一音节 `qing` 下的六个常用字，展示三段编码如何逐步收敛：

| 字 | 全拼 | ＋结构 | ＋部首 | 部首来源 |
|:--:|---|---|---|---|
| 请 | `qing` | `qingz` 左右 | `qingzy` | 讠→言→**y** |
| 轻 | `qing` | `qingz` 左右 | `qingzc` | 车→车→**c** |
| 清 | `qing` | `qingz` 左右 | `qingzs` | 氵→水→**s** |
| 情 | `qing` | `qingz` 左右 | `qingzx` | 忄→心→**x** |
| 晴 | `qing` | `qingz` 左右 | `qingzr` | 日→日→**r** |
| 青 | `qing` | `qings` 上下 | `qingsq` | 青→青→**q** |

再看「应」——本输入法的图标字：

```text
应  →  ying          全拼
    →  yingb         半包围结构（广字头）
    →  yingbg        部首「广」→ guǎng → g
```

### 各段的实际区分力

按字频加权统计：

| 输入到哪一段 | 附加键 | 唯一编码占比 | 目标字排第一 | 平均同码候选 |
|---|---:|---:|---:|---:|
| 仅全拼 | 0 | 5.3% | 57.3% | 38.0 |
| ＋结构码 | 1 | 25.5% | 73.9% | 14.4 |
| ＋部首码 | 2 | 67.5% | **94.1%** | 2.2 |

打满三段时，目标字有 94.1% 的概率就在第一位；查看前三个候选则覆盖 99.6%。

实际使用中并不需要每次打满：裸全拼时已有 57.3% 的字排在第一位、80.4% 在前三。按「一直加码直到目标字排第一」的保守口径计算，平均每字只需 0.685 个附加键。

## 1.6 词组

基础码是各字全拼**直接连接**，中间不加分隔。支持 2—12 字词组。

以这首诗为例：

> 秋風紅葉時，諸辰燒雲落。明月白霜裏，天地一出新。

词库收的是简体，下面的编码示例相应写作「秋风红叶时，诸辰烧云落。明月白霜里，天地一出新。」

### 基础码已唯一的情形

**76.4% 的词条基础码就是唯一的**，不需要任何后缀：

```text
baishuang   →  白霜        唯一候选，打完即可上屏
```

### 需要一级后缀的情形

基础码撞车时，对**第一个能分开候选的歧义字**追加一组「结构＋部首」：

```text
qiufeng     →  秋风 球风              两个候选
qiufengzh   →  秋风                   秋：左右(z)＋禾(h)

hongye      →  红叶 鸿业              两个候选
hongyezs    →  红叶                   红：左右(z)＋丝(s)

mingyue     →  明月 名曰              两个候选
mingyuezr   →  明月                   明：左右(z)＋日(r)

chuxin      →  出新 初心              两个候选
chuxinsq    →  出新                   出：上下(s)＋凵(q)
```

### 需要二级后缀的情形

一组后缀仍分不开时，最多再追加第二组（针对另一个歧义字）：

```text
tiandi        →  天地 田地 天敌 天帝 田底     五个候选
tiandidd      →  天地 天敌 天帝               天：独体(d)＋大(d)，剩三个
tiandiddzt    →  天地                         地：左右(z)＋土(t)，唯一
```

**不会有第三组**——分不开就保留候选列表，不伪造唯一编码。

### 未收录的词怎么办

词库是静态的，「秋风红叶」「明月白霜」这类搭配并未收录。这时按词或按字分段输入即可：

```text
秋风红叶  →  qiufengzh  +  hongyezs
明月白霜  →  mingyuezr  +  baishuang
```

单字同理，逐字打各自的完整码：

```text
诸 zhuzy    辰 chenbc    烧 shaozh    云 yunse    落 luosc
```

### 分布

| 词条情况 | 数量 | 占比 |
|---|---:|---:|
| 只有基础码 | 411,356 | 76.39% |
| 含一级后缀（＋1~2 键） | 97,297 | 18.07% |
| 含二级后缀（＋3~4 键） | 29,832 | 5.54% |

基础码、一级码、二级码**同时有效**，可按需要逐步加码，不必一次打对。

## 1.7 标点符号

中文模式下，标点自动转为**全角中文标点**：

| 按键 | 输出 | 按键 | 输出 | 按键 | 输出 |
|:--:|:--:|:--:|:--:|:--:|:--:|
| `,` | ， | `.` | 。 | `;` | ； |
| `:` | ： | `?` | ？ | `!` | ！ |
| `\` | 、 | `<` | 《 | `>` | 》 |
| `(` | （ | `)` | ） | `[` | 【 |
| `]` | 】 | `{` | 「 | `}` | 」 |
| `'` | ‘ ’ | `"` | “ ” | `^` | …… |
| `_` | —— | `~` | ～ | `$` | ￥ |
| `@` | ＠ | `#` | ＃ | `%` | ％ |
| `&` | ＆ | `*` | ＊ | `+` | ＋ |
| `-` | － | `=` | ＝ | `/` | ／ |
| `` ` `` | ｀ | `\|` | ｜ | | |

引号成对：单引号在 `‘` 与 `’` 之间交替，双引号在 `“` 与 `”` 之间交替。

切换到**西文模式后标点原样输出**——那时输入法完全透明，按键根本不经过引擎。

实现上，标点键由文本服务通过 `ToUnicodeEx` 按当前键盘布局解析成 ASCII 字符后交给 librime，再由 `punctuator` 处理器配合 `punct_segmentor` / `punct_translator` 转为中文形式。按布局解析而非写死键位，是因为 `?` 在不同键盘布局上并不在同一个物理键。

## 1.8 中文／西文切换

**轻敲一下 Shift** 在中文和西文之间切换。切到西文后输入法完全透明，所有按键直接交给应用。

语言栏上有一个按钮显示当前模式（「中」或「西」），**点它也能切换**，因此不必先知道 Shift 这个快捷键。

模式存放在 TSF 的 `GUID_COMPARTMENT_KEYBOARD_INPUTMODE_CONVERSION`，而非各进程的引擎内。该 compartment 在用户会话内全局同步，因此**在任何一个应用里切换，所有应用立即生效**；Windows 自己也读这个标志，shell 会显示它自带的中／英指示。引擎的 `ascii_mode` 只由 compartment 事件回调写入，不存在第二个真相来源。

预留键注册为 `VK_SHIFT + TF_MOD_ON_KEYUP`，只在 Shift 单独按下并释放时触发，因此 `Shift+字母`、`Shift+方向键` 等组合不受影响，也不会遮蔽编辑器快捷键。

## 1.9 容错码

`data/hengma_fuzzy.dict.yaml` 收录 70,665 条容错码，覆盖漏键与邻键换位等常见手误（如 `qing` 误打成 `qig`、`iqng`）。容错码权重远低于正规码，不会抢占正常候选的位置；实测只有 5 个容错码与正规码字面重合（占正规码的 0.07%），污染可以忽略。

## 1.10 候选窗上的编码注释

候选窗里每个单字后面标出它自己的**完整编码**，便于边打边学：

```text
qing  →  请 qingzy   轻 qingzc   清 qingzs   青 qingsq   情 qingzx
ying  →  应 yingbg   影 yingzs   英 yingsc   营 yingsc   迎 yingbz
```

多音字只显示与当前输入相符的那个读音：打 `hang` 时「行」标 `hangzx`，打 `xing` 时标 `xingzx`。词组候选不加注释。

注释数据来自 `data/hengma_char_codes.dict.yaml`，由 `data-tools/generate_codes.py` 从单字词典派生——对每个字保留所有「不是其它码前缀」的极大码，即每个读音一条完整码。

这一步没有走 librime 的 `reverse_lookup_filter`：librime 的部署器只编译 `translator/dictionary` 指定的那一本词典，从过滤器引用的反查表不会被构建；而直接反查 `hengma` 会连容错码一起返回（「清」会得到 `ing`、`qig`、`qnig` 等二十余条）。因此注释由文本服务自己完成。

# 六、打包与安装

## 6.1 生成安装程序

```powershell
./installer/setup/make-setup.ps1
```

依次构建两个架构、把 `dist/Yingwu` 压成 LZX 的 CAB、生成载荷元数据，再把 CAB 与卸载程序一并嵌入 `dist/YingwuSetup-<版本>.exe`，并写出 SHA-256。

产物是**单个约 8.8 MB 的 exe，任何 x86/x64 的 Windows 都能直接双击运行**：

- 32 位构建（`/MT` 静态 CRT），一个文件覆盖两种架构；32 位系统上自动跳过 x64 载荷
- **无任何前置依赖**，不需要 VC++ 运行库（`rime.dll` 只依赖 `kernel32` / `user32` / `dbghelp`）
- 清单为 `requireAdministrator`，双击即请求提权
- 按 x86 → x64 顺序，分别在两个注册表视图注册文本服务
- 在「应用和功能」写入卸载项

命令行参数：

```bat
YingwuSetup-0.57-heng.exe /silent
YingwuSetup-0.57-heng.exe /dir="D:\Yingwu"
```

## 6.2 安装过程做了什么

**可回滚**：载荷先解压到 `<安装目录>.new` 并校验关键文件，通过后才注销旧版本、逐个覆盖。解压或校验阶段失败不会动到已有安装。被运行中程序占用的 DLL 会改名并登记为重启后删除，因此覆盖安装不必先关掉所有应用。

**沙箱授权**：给安装目录授予 `ALL APPLICATION PACKAGES`（SID `S-1-15-2-1`）与 `ALL RESTRICTED APPLICATION PACKAGES`（`S-1-15-2-2`）的读取与执行权限。Edge、所有商店应用以及越来越多的沙箱化程序运行在 AppContainer 里，**没有这项授权就根本加载不了输入法 DLL**。两个组按 SID 而非名称寻址，因为它们的显示名是本地化的。同时为当前用户创建并授权 `%LOCALAPPDATA%\Yingwu\Rime`。

**旧版清理**：检测并移除 0.3.0-alpha 遗留的「衡码输入法」安装（`%ProgramFiles%\Hengma`、`HKLM\SOFTWARE\Hengma` 及其卸载项），避免升级后输入法列表出现两个条目。

## 6.3 卸载

控制面板「应用和功能」，或直接运行 `%ProgramFiles%\Yingwu\YingwuUninstall.exe`：

- `/silent` 静默卸载
- `/purge` 连同 `%LOCALAPPDATA%\Yingwu` 一起删除（默认保留，便于重装后免去重新编译词库）

## 6.4 脚本安装（开发期）

```powershell
./installer/Install-Yingwu.ps1      # 卸载：./installer/Uninstall-Yingwu.ps1
```

## 6.5 图标

图标是「应」字（`yingbg`），由 `scripts/make-icon.ps1` 渲染成 10 种尺寸的多分辨率 `.ico`：16—24 px 去掉底板、放大字面以保证可读，32 px 以上使用圆角深色底板。文本服务与安装程序共用同一个图标。

```powershell
./scripts/make-icon.ps1 -Out src/TextService.ico
```

字体为**思源黑体 / Source Han Sans**（OFL-1.1），可自由再分发。脚本在渲染前校验字体家族确实存在，找不到即报错退出——GDI+ 在字体缺失时会静默替换成默认字体，那样会把错误的字形悄悄发布出去。

# 七、诊断日志

文本服务跑在别人的进程里，没有控制台也没有自己的界面，出问题时用户只会看到「按键没反应」。因此它会向下面这个文件追加简短的事件轨迹：

```text
%LOCALAPPDATA%\Yingwu\yingwu.log
```

```text
2026-09-23 18:44:26.222  [25160] engine-start: C:\Program Files\Yingwu\x64
2026-09-23 18:44:32.881  [25160] dictionaries-built: 6641 ms
2026-09-23 18:44:32.882  [25160] engine-ready: 8183 characters
2026-09-23 18:55:03.858  [3044] mode: western
```

记录的是事件，**不记录任何输入内容**——编码、候选、上屏文本都不会写入。这是产品承诺的一部分（工程方案 §9.3「安全审查确认不记录用户输入正文」），修改 `src/Diagnostics.*` 时必须守住。

文件超过 256 KB 会被截断重写；日志只用于排查当下的故障，不留历史。目录不可写时日志自行关闭，不影响输入。

# 八、设计说明

```text
Windows 应用
  → TSF / CTextService
  → RimeEngine 适配层（按绝对路径安全加载）
  → 随包 rime.dll
  → 静态词典
  → TSF 组合文本 ＋ 原生候选窗
```

输入内容不上传。当前 alpha 版把 librime 加载进应用进程；稳定版应评估改为独立宿主进程，以降低第三方应用被输入法故障波及的风险。

COM 边界（`_IsKeyEaten`、`OnKeyDown`、`OnPreservedKey`）均有异常防护——异常逃逸出 `STDMETHODIMP` 是未定义行为，在文本服务里会连带宿主应用一起崩溃。
